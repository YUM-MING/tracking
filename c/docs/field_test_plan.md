# 필드 테스트 계획서 (노량진 테스트 매장, 9월)

8월 말 회의 지시사항의 구현: 테스트 시나리오 · 튜닝 방법론 · 변경 반영 확인 ·
데이터 보안 설계 · 장애 대응 매뉴얼을 한 문서로 정리한다.
([회의록](meeting_2026-08_field_test.md) 참고)

---

## 1. 목적과 범위

- **목적:** 실제 매장 환경에서 ① 판정 임계값을 매장 실측 데이터로 튜닝하고
  ② 24시간 무중단 운영이 가능한지 검증한다.
- **장소/기간:** 노량진 테스트 매장 (우선 팀장님 매장), 9월 중 — 사전 검증 통과 후 투입.
- **범위 제외:** 2층 매장, 야간 전용 운영 (추후 별도 논의).

## 2. 투입 전 사전 검증 (Go/No-Go 체크리스트)

기존 매장 운영에 영향이 없음을 수치로 확인한 뒤에만 현장에 투입한다.

**1시간 연속 가동 (개발 환경):**
- [ ] CPU 점유율 피크 ≤ 15% (리소스 모니터 5초 주기 실측, 로그에 기록됨)
- [ ] RSS(메모리) 증가 추세 없음 (누수 확인 — 시작 대비 ±10MB 이내)
- [ ] WS 전송 실패·백로그 폐기 0건 (`[ws]` 로그 확인)
- [ ] 네트워크 전송량 실측 (이벤트 JSON뿐이므로 시간당 수 KB 수준이어야 정상)

**24시간 연속 가동:**
- [ ] 크래시 0회 (재시작 이력 `restarts.log` 비어 있음)
- [ ] 하트비트 결손 0회 (수신 모니터 기준)
- [ ] 날짜 넘어갈 때 JSONL 파일 롤오버 정상 (`data/` 날짜별 파일 확인)
- [ ] 영업시간 외 저전력 전환/복귀 정상 (`[모드]` 로그)

## 3. 튜닝 방법론 — 어떤 데이터로 무엇을 조정하나

| 데이터 소스 | 튜닝 대상 | 방법 |
|---|---|---|
| `data/journeys_*.jsonl` (퇴장 손님 1명 = 1줄) | 체류 알림 기준(300초), 키오스크 근접 비율(13%), 배회 기준 | 체류 시간 분포·키오스크 전환율을 pandas로 뽑아 기본값을 매장 실측 분포로 교체 |
| 오탐 신고 (`/api/fpstats`, 점주 페이지 버튼) | 룰별 민감도 (쓰러짐 종횡비, 확정 프레임 수 등) | 알림마다 진짜/오탐 라벨링 → 오탐율 5% 초과 룰은 자동 보수화 (폐루프 내장) |
| `data/events_*.jsonl` (알림 1건 = 1줄) | 쿨다운, 알림 빈도 | 시간대별 알림 횟수 집계 — 하루 알림 수가 과하면 룰이 맞아도 제품 실패 |
| `--log=` 파일 + 리소스 모니터 | 추론 주기, 절전 파라미터 | 피크 CPU/RSS, 단계별 추론 시간(profiler)으로 detect_every_n 조정 |

**일일 튜닝 사이클:**
가동 → JSONL·오탐 라벨 축적 → 저녁에 분포 확인 → 점주 페이지 슬라이더로 수정
(재빌드 없음) → 다음 날 같은 지표 비교. 목표: 3~5일 내 일 오탐 알림 5건 이하.

## 4. 변경 반영 확인 방법론 (회의 지적사항)

원격(웹)에서 값을 바꿨을 때 실제 적용 여부를 확인하는 3중 장치 — 이미 구현됨:

1. **버전 번호:** 설정 저장마다 `store_settings.json`의 `version`이 증가.
2. **적용 로그:** 파이프라인이 새 버전을 집어들면 `[설정] 점주 설정 v N 적용
   (이전 v M)` 로그가 찍힘 — 이 한 줄이 반영 증거.
3. **재조회:** `GET /api/settings`로 현재 적용값과 버전을 언제든 원격 확인.

절차: 값 변경 → `/api/status`의 `settings_version` 증가 확인 → 로그에서 적용
라인 확인. 10초 내 미반영이면 장애 매뉴얼 D항 참조.

## 5. 데이터 보안 설계 (1차 디텍팅 → 2차 필터링 → 3차 전송)

| 단계 | 데이터 | 어디까지 가나 |
|---|---|---|
| 1차 디텍팅 | 원본 프레임 | **엣지 메모리에만 존재** — 디스크 저장·전송 일절 없음 |
| 2차 필터링 | 트랙 ID, 구역 판정, 동선 단계 | 엣지 로컬 (JSONL·로그) — 이미지·얼굴·개인정보 없음 |
| 3차 전송 | 필터링된 이벤트 JSON ("몇 명이 뭘 하는지") + 하트비트 | WS로 서버 전송 — 네트워크에 이미지를 태우지 않는다 |

- 점주 페이지 실시간 화면도 좌표 오버레이만 전송한다 (영상 스트리밍 아님).
- 현장 데모 등에서 화면을 보여줘야 할 때는 **비식별 모드**(`--privacy`)로 실행 —
  영상을 열화상풍으로 뭉개고 박스/스켈레톤만 또렷이 표시한다.

## 6. 운영 도구 (이번에 추가)

| 도구 | 역할 | 사용 |
|---|---|---|
| 하트비트 송신 | 1분마다 생존 신호를 WS로 전송 (uptime/CPU/RSS/인원/FPS 포함) | `--ws=` 설정 시 자동 |
| `tools/heartbeat_monitor.py` | 수신 서버: 이벤트·하트비트 기록 + **3분간 신호 없으면 알림** + 오래된 수신 파일 자동 정리 | `python3 tools/heartbeat_monitor.py --port 8080` (집/사무실 컴퓨터에서) |
| `tools/run_forever.sh` | 크래시 시 자동 재시작 + `restarts.log`에 이력 기록 (정상 종료 `q`는 재시작 안 함) | `tools/run_forever.sh --no-window --ws=...` |

## 7. 장애 대응 매뉴얼

완벽한 시나리오는 불가능하다는 전제로, 증상별 1차 대응을 정한다.
공통 원칙: **모든 대응의 첫걸음은 로그 확보** (`pipeline.log` 마지막 200줄 + `restarts.log`).

| # | 증상 | 감지 경로 | 1차 대응 | 원인 확인 | 예방 |
|---|---|---|---|---|---|
| A | 프로그램 크래시/종료 | 하트비트 끊김 알림 | `run_forever.sh`가 자동 재시작 — 복구 확인만 | `restarts.log`의 종료 코드 + `pipeline.log` 마지막 줄 | 24시간 사전 가동 검증 |
| B | 프로세스는 살았는데 판정 멈춤 (행) | 하트비트는 오는데 infer_fps=0 | 팀뷰어 접속 → `q` 종료 → 재시작 | 로그에서 마지막 `[판정]`/`[캡처]` 태그 시각 확인 | 프레임 정지 자가 진단(5초)이 이벤트 발행 |
| C | 카메라 이상 (백화/블랙아웃/프리즈/단선) | `EV_HW_FAULT` 알림 (자가 진단 내장) | 점주에게 렌즈/전원 확인 요청 — 30회 연속 실패 시 자동 재연결됨 | `[카메라]` 태그 로그 | 설치 시 직사광·역광 회피 (설치 제안서) |
| D | 설정 변경이 반영 안 됨 | `/api/status` 버전 그대로 | 설정 재저장 → 그래도 안 되면 재시작 | `store_settings.json` 파일 권한/디스크, `[설정]` 로그 | 반영 확인 절차(4장)를 습관화 |
| E | 수신 서버(AWS 등) 장애 | 서버 측 접속 불가, `[ws] 연결 실패` 로그 | **엣지는 그대로 둔다** — 이벤트는 백로그(500건)에 보존, 서버 복구 시 자동 재연결·전송 | 서버 콘솔/상태 페이지 | 엣지는 서버 없이도 완결 동작하는 설계 (로컬 JSONL이 원본) |
| F | 잘못된 배포 (패치 후 이상) | 배포 직후 하트비트/FPS 이상 | 직전 바이너리로 롤백 (배포 전 `kiosk_tracking.bak` 보관 규칙) | 새 버전 로그와 직전 버전 로그 비교 | 배포 직후 10분 관찰을 절차화 |
| G | CPU 폭주/발열 | 리소스 모니터 85% 경고 로그 | 점주 페이지에서 분석 주기 상향(추론 감속) | `[리소스]` 태그, profiler 단계별 시간 | 절전·영업시간 모드 활성화 |
| H | 디스크 참 (로그/JSONL 누적) | 쓰기 실패 로그 | 오래된 `data/`·로그 파일 삭제 | `df -h` | 수신 모니터의 자동 정리(기본 7일) + 월 1회 점검 |

**에스컬레이션:** 하트비트 알림 수신 → 5분 내 원격 접속 → A~H 매뉴얼 대응 →
30분 내 미복구 시 현장 방문. 모든 장애는 로그를 첨부해 당일 기록으로 남긴다.

## 8. 성공 판정 기준 (테스트 데이터로 다음 단계 결정)

- 가동률 ≥ 99% (하트비트 기준), 크래시 자동 복구 포함
- 일 오탐 알림 ≤ 5건 (튜닝 완료 후 연속 3일)
- 동선 기록과 실제 결제 내역 대조 정합률 ≥ 90% (journeys JSONL vs POS)
- CPU 피크 ≤ 15%, 이미지 외부 전송 0건 (설계상 불가능함을 로그로 증빙)
