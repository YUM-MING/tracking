# 8월 말 회의 (필드 테스트 준비)

#### ① 필드 테스트 사전 계획 수립 (시나리오 필수)

- **세부 계획 없이는 투입 불가:** 어떻게 테스트할지, 문제가 생기면 어떻게 할지,
  수정은 어떻게 반영할지 — 시나리오를 전부 세워놓고 들어가야 함.
- **파라미터 외부화:** 판정 파라미터를 파일로 매핑해 저장/로드하고, 웹서버를 하나
  두어 원격(집 IP)에서 값을 조정할 수 있게 할 것. 쌓이는 파일은 하루 1회
  클리어하는 식의 관리 정책 포함.
- **변경 반영 확인 방법론:** 웹에서 값을 바꿨을 때 실제로 파이프라인에 적용됐는지
  **확인하는 방법**까지 정해놓고 테스트에 들어가야 함.

#### ② 운영 안정성 및 장애 대응 (무중단이 신뢰)

- **사전 부하 검증:** 기존 서비스(매장 운영)에 영향을 주는지 미리 상상해서 검증할
  것 — 1시간 연속 가동 시 CPU 점유율, 네트워크 전송량(인풋/아웃풋)을 실측하고,
  하루 연속 가동 테스트까지.
- **죽었을 때의 대응:** 하루 돌리다 프로그램이 꺼지면 팀뷰어 원격으로 재기동해야
  하는 상황이 옴. 이때 **원인을 바로 추측할 수 있는 로그**가 반드시 남아 있어야 함
  (내 프로그램 문제일 확률이 제일 높으므로).
- **하트비트(생존 신호):** 1분마다 신호를 보내게 하고, **신호가 안 오면 나에게
  알림**이 오게 할 것. 잠깐 꺼져도 신뢰도 하락 + 기회비용으로 손해가 큼 —
  꺼지면 안 된다.
- **배포 검증 문화:** 새벽 4시 자동 배포라도 현장에서 잘 켜졌는지 확인할 정도로
  검증함. 프로그램에 완전한 믿음은 있을 수 없음.
- **대응 매뉴얼:** 완벽한 시나리오는 불가능하므로 **장애별 대응 매뉴얼**을 짤 것 —
  AWS가 뻗었을 때, 배포가 잘못 나갔을 때(NHN 사례) 등. 시간당 계약(SLA)을 쓰는
  세계이므로 운영 관점에서 프로그램을 봐야 함.

#### ③ 데이터 보안 및 프라이버시 (전송 설계)

- **3단 구조로 짤 것:** 1차 디텍팅 → 2차 필터링 → 3차 데이터 보안/전송.
- **이미지는 네트워크에 태우지 않는다:** 대부분의 현장이 카메라 영상 반출을
  막아놓음. 서버로는 **필터링된 데이터만** 전송 ("몇 명이 뭘 하고 있는지" 수준).
  매장 내부에서만 쓰는 데이터는 그대로 둬도 됨.
- **카메라 거부감 해소:** 어느 회사든 감시당하는 느낌 때문에 카메라를 싫어함.
  이미지를 써야 한다면 열화상처럼 뭉개서(비식별화) 표시 — 안전 분야 CCTV가
  열화상처럼 나오는 이유. 결국 승부는 **필터링(판정) 정확도**로.

#### ④ 필드 테스트 일정 및 장소

- 시나리오를 제출하면 → 타당성 검토 → **노량진 테스트 매장**에서 튜닝,
  **9월 진행** 여부 결정.
- 우선은 팀장님 매장으로 시작. 2층 매장·야간 운영 케이스는 추후 논의.
